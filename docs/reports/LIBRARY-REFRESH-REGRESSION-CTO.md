## 已确认根因与用户新选择

先阅读 MVP、V0.2 与工作流，再检查轮询、排序、缓存和锚点实现。服务端应用库按首次发现时间与 ID 排序；前端当时会自动应用后续成功结果。顶部/筛选控件仍可见时，旧实现也把第一个可见应用行当作恢复锚点，因此首部新增应用会主动向下滚动。

隔离 Chrome、817×863 的修复前红测试：`scrollY=0 / h1.top=163`，插入一行并应用后变为 `scrollY=90 / h1.top=73`，退出码 1。这个证据证明可复现的前端缺陷，不证明正式用户反馈只有该原因。正式页面前置观察由 CEO 单独记录在部署报告。

用户随后明确改选“保持当前清单，有新数据时提示，点击后更新”。本轮以这一新选择覆盖原 #21 自动应用要求；未通过停止后台检测来保持清单。

## 实现与关键边界

同一完整查询在原会话缓存条目中分别保留显示快照与最新待应用快照，仍只有一套最多 20 条查询的有界缓存。仅 `/apps?…` 启用此策略；其他资源继续自动更新。首次无缓存成功返回立即显示；之后每 15 秒成功检测仅更新待应用结果，显示中的行、顺序、内容、总数及页码保持不变。JSON 等值比较忽略对象字段顺序、保留数组顺序；相同结果保持原数据引用且不产生提示，最新结果回到当前显示值时移除旧提示。

“更新清单”采用已经成功取得的最新待应用结果，不需要额外请求。全局“刷新当前数据”先取得新成功结果，再走同一应用流程；失败保留原显示与已有待应用资料。多个触发仍共享同键单次请求；后台再有更新重新暂存，不延续一次点击为永久自动应用。

有效页切换采用两阶段处理：如果新总数使当前页失效，先保留旧页完整快照及待更新提示，取得目标有效页的最新成功响应后，才同时切换行、总数和 offset。目标请求慢或失败时，不先展示旧目标页缓存。若请求过程中总数再次减少，最多再回到第一页，避免无限追逐变化页码。异步期间查询改变、离开页面或会话取消后不会回写当前视图；未提交的搜索输入也不被较早操作覆盖。

详情返回恢复原显示快照和待更新提示。顶部/控件区域保持原 viewport，真正进入列表正文才使用 app ID 锚点；没有实际位移不调用滚动。提示及后台失败文案占固定高度区域，不把表格向下推。相对“最近采集”时间使用显示快照时间计算，避免仅因检测重渲染而改变行内文案。817px 图标导航补充可访问名称和 title，方便键盘、辅助技术及自动化准确定位应用库。

缓存 API 保留通用语义并增加可测试入口：`stageUpdates(key)`、`pendingData/hasPending/displayedAt`、`applyPending(key)` 与 `fetch(key,{apply:true})`。登出、会话失效、缓存淘汰和请求世代保护同时作用于两个快照，未增加持久浏览器缓存。
