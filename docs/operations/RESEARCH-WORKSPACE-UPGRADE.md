# 研究工作台升级与恢复

适用于 #42 / 008 增量迁移。它新增 `research_*` 关系表，不重建或删除已有市场、历史、原始响应和采集任务表。原采集协调器继续持有单进程锁，新增 Web 流程不会创建第二套采集器。

## 升级顺序

1. 在隔离构建目录执行前后端构建和自动/API/浏览器回归，保留当前 `dist` 发布目录及 `.env`。不要在运行服务使用的 `dist/client` 边构建边覆盖。
2. 停止 launchd 服务，等待正在执行的商店请求正常退出及 3000 监听/采集锁释放。使用 `launchctl bootout` 防止 KeepAlive 立即拉起旧进程。确认没有其他 CLI 或 worker 使用同一数据库。
3. 对停写后的 SQLite 做完整一致性备份。可使用 SQLite online backup；已确认无连接时可 checkpoint 后复制主库。APFS 克隆只在停写/检查点完成后使用；不能直接复制活跃的主文件而漏掉 WAL。记录备份大小、时间、旧应用身份/人工分类、重要表数量与任务/批次游标。
4. 原子替换经过检查的发布目录。首次启动前先在无采集环境应用迁移并比较旧表关键摘要及固定 cohort，确认只新增研究结构。迁移由 `schema_migrations` 记录，事务失败回滚。
5. 启动唯一 launchd 服务，检查真实 `/api/health`、平台登录、当前角色、市场列表/详情和采集器周期/进度。旧管理员会话升级后需重新登录，因为已由内存签名 Cookie 改为服务器持久随机会话。
6. 平台创建客户空间、邀请首位管理员；不迁入原型客户、示例研究或测试账号。记录正式 URL、版本、迁移结果、备份与实际采集恢复情况，再执行最终验收/关闭议题。

## 回滚

先停止唯一服务并等待锁释放。恢复升级前发布目录；008只增加表，旧程序可以继续读取原市场结构。如果升级后已保存客户研究，不能直接用旧整库覆盖而丢弃新研究或后续采集。通常仅回滚代码，保留新增表并关闭新入口。

只有明确需要整库恢复、且已另存升级后数据时，才恢复一致性数据库备份及配套文件；旧 WAL/SHM 不能与不同时间点主库混用。再次启动前核对数据库 dataset、分类、批次和单写进程。`.env`、数据库、会话、密码哈希和明文邀请链接不提交 Git；备份存于受控本地目录。

## 性能与证据边界

只读抽样副本可证明真实字段映射和客户功能，不能冒称全库迁移、完整事件统计或线上性能验证。记录副本选择规则和缺少的历史。最终上线应另记录完整备份、真实库规模、迁移前后不变摘要以及实际 API 用时。原 #11 的固定 2,024 成员不因新的小时记录、客户申请或本次升级扩张。
