## 目标与范围

用户要求扫描泰国、墨西哥、菲律宾、巴基斯坦、印度尼西亚、阿根廷的财务类应用，识别信贷并保存；对所有已经入库的应用尽可能采集完整信息，有多少可取得信息就保存多少。

本轮将两个任务分开计数：**市场发现**采用六国两商店可访问的财务榜单和当地关键词，完整发现集合及已取得详情先保存到批次暂存记录（staging），再按信贷证据决定新增主应用库记录；**资料补齐**覆盖启动时已入库应用及本次新增主应用库记录，不因分类而跳过。新增发现和后续采集可分批运行，但必须使用同一运营批次标识与可恢复进度。

Google Play 和 App Store 的公开榜单、搜索与采集库并不提供可证明完整的商店应用枚举。因此，本轮“扫描完成”只表示已完成记录中的可获取发现来源及应用资料采集计划，不表示已找到这些国家的全部财务或信贷应用，也不用于推算完整市场份额。

### App Store 搜索的已核实边界

PM于2026-09-07读取[Apple官方存档：Constructing Searches](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/iTuneSearchAPI/Searching.html)（页面更新日期2017-09-19）。该存档写明搜索`limit`为1–200、默认50；`country`指定店面，搜索返回语言`lang`仅列`en_us`与`ja_jp`，默认英语；Search API约每分钟20次调用且可能变化。它是接口参考，不是新的法律政策，也不能替代本轮真实调用结果。

本轮App Store每关键词按最多4批×50条处理至多200条公开搜索结果。批次、上游实际请求和分页机制分别记录；若库将一次返回在本地切分，应记为本地切分，不能声称存在4个独立上游游标页。当地语言关键词、请求店面、实际搜索`lang`与评论请求语言分别保存；使用当地词语搜索不证明搜索返回或评论均为该国语言。

运行计划对iTunes `/search` 与 `/lookup`合并设置至少3100ms请求间隔，其他请求设置至少500ms全局间隔，并计入库内部请求。前者是本轮依据官方存档采用的保守执行设置，后者是本地执行配置；二者都不是“商店保证不会限流”的承诺，遇实际限流仍要退避并保留进度。

## 2. 信贷识别与人工覆盖

沿用已验收的 `strong / possible / insufficient` 识别方法和人工优先规则，不在扫描脚本中另外发明一套信贷标签：

- 本轮扫描中新发现且主应用库尚不存在的对象，strong以auto模式进入主应用库并成为confirmed；possible进入主应用库并成为candidate；insufficient仅保留staging及全部已取得资料，不新建主应用库App。Finance分类或loan关键词本身不是确认信贷的证据。此处是一次性批次的入库筛选，不改变v0.2普通新增App的默认分类规则。
- 原有manual与legacy的有效classification全部保留。旧应用即使新分析为strong，也只更新自动建议，不自动解除人工覆盖。
- 人工excluded不会重新变成confirmed，也不会因本轮搜索再次命中而撤销排除；但用户要求所有入库App补齐资料，因此excluded仍要尝试数据采集。
- 主应用库原有App即使本轮分析为insufficient也保留并执行全部补齐任务，不能迁出主库或缩小覆盖分母。
- 报告分别统计发现暂存总数、暂存未入库数、有效confirmed、自动strong建议、人工/legacy覆盖以及新增候选；不得把这几种数量混称为“新发现信贷”。
- 版本化自动分析与原文观测时间分开记录。对已有数据重算规则不制造新的商店快照或首次发现日期。

本轮不得为了提高“识别率”批量解除人工覆盖、删除主库弱证据应用或暂存原始资料，或将财务类应用统一改为信贷。

## 3. 所有入库应用的资料采集

每个清单内App至少具有本轮以下任务的可追溯结果；此前成功数据可以保留，但不能代替本轮尚未执行的尝试：

1. **详情**：刷新应用完整资料、当前描述、商店发布者/法律实体/seller等可用字段，保存规范字段、完整返回与原始证据；更新识别建议但尊重人工覆盖。
2. **评论**：在该国家/语言/商店接口实际支持的范围内，逐页取得全部可获取评论，不停在v0.2的近期样本默认窗口。
3. **七类补充**：permissions、dataSafety、privacy、versionHistory、inAppPurchases、ratings、developer。每种都应明确结果；商店不支持的组合登记unsupported，不捏造对应资料。

某类失败不能阻止其他资料继续采集。权限/隐私/开发者等可独立执行时，不因详情失败一概跳过；确需详情返回ID等前置条件的任务，记录依赖失败及可恢复状态，不能冒充unsupported或成功空返回。

成功返回的未知字段、嵌套数据、原始搜索行、评论及补充资料都保存，主应用库延续v0.2的可展开/分页/API能力；staging资料通过可定位的本地批次记录读取，不为此新增后台界面。不得只保留汇总条数或精选字段。资料来自商店声明，不等于实际设备权限、完整Manifest或公司/牌照核验。

## 4. 评论分页与终止原因

CTO 依据实际库能力记录每个商店的分页方式、排序、语言和页大小。对每个应用/国家/语言流保存页号或cursor、请求时间、返回数、新增稳定ID数、更新数、错误和下一步位置。

| 结果 | 何时可采用 | 验收含义 |
| --- | --- | --- |
| 自然结束 | 上游明确无next cursor/hasNext，或按已核实接口契约返回终止空页。 | 当前接口上下文可获取评论已遍历，不能扩张为全商店/所有语言历史评论。 |
| 上游限制 | 已证明存在最大页数、返回窗口、地区可见性或接口不提供继续位置。 | 标注具体方法、上限/现象和实际覆盖；可按已知限制完成该来源，不声称全量。 |
| 无进展保护 | cursor重复或连续重复页，无法安全继续。 | 保存已取得资料和最后位置，标明保护停止；不自动冒充自然结束，需复核接口行为。 |
| 暂时失败 | 网络、限流、超时或可恢复结构异常。 | 有限重试及退避，保留上次成功、失败页和恢复游标；未解决时保持待恢复或明确失败。 |
| 运行切片/进程中断 | 本轮执行分批、重启或停止。 | 持久保存最后成功页和下一步位置，继续时幂等恢复。它不是该App评论采集完成。 |

禁止人为设置“每App前N页”“只取最新100条”后将其记为完整完成。可以分批处理以控制单次运行时间，但未完成页须留在队列/检查点并继续。若上游库本身有真实上限，报告真实能力边界，不能把本地切片上限说成商店上限。

稳定评论ID按跟踪App去重；重复页或恢复重放不增加重复评论。评论修改可以更新既有记录，新增数与更新数分开。若上游无稳定ID，沿用带来源说明的内容标识，明确其限制。评分人数和商店聚合评论数量不能直接当作公开接口必须返回的文本评论总数。

## 5. 运行与恢复

- 使用现有单主机数据库和单活动worker边界，避免运营脚本与后台worker同时争抢同一任务或并行写入不兼容的游标。
- 请求遵守实际限速，包含库内部请求；遇429、超时等保存错误并有限退避。不能以无界并发换取完成速度。
- 任务及分页进度持久化。重启后可从最后成功位置恢复；游标敏感时留在被忽略的本地数据中，GitHub报告只记录存在性/摘要，不公开访问凭据。
- 失败不覆盖最近成功数据、时间和上下文；最新尝试与上次成功分开。成功空返回、unsupported、依赖失败、未尝试和普通失败不得混同。
- 本轮不改国家关键词、采集周期或用户分类偏好。运行必要的暂停/恢复需记录实际状态，结束时恢复原先运行设置。
- 真实库、备份和大体积原始资料留在受控本地存储；GitHub提交需求、方法、统计、脱敏错误与验收证据，不提交凭据或真实评论正文/用户名。

## 7. 完成与报告口径

最终报告至少包含：

- 批次标识、开始/结束时间、依赖/代码/识别规则版本、真实数据集和恢复记录。
- 六国两商店来源覆盖矩阵，榜单/搜索各自的实际能力和终止原因。
- 原应用数量、发现暂存数量、暂存未入库数量、新增主库应用数量、最终主库补齐清单数量及去重规则；有效confirmed与自动strong建议分别统计。
- 对详情、评论、七类补充逐项给出已尝试、成功有数据、成功空、不支持、失败、依赖阻塞、未尝试、待继续数量。
- 评论页数、实际留存数量、自然结束/上游限制/无进展/失败/待恢复分类；已知上游限制可定位至方法与实际证据。
- 人工/legacy分类前后对照、数据库一致性、原数据未丢失以及恢复检查结果。

只有全部范围已执行、没有内部阻断和未完成恢复项时，才可写“本次可获取范围采集完成”。若剩余项全部是证据明确且无法在本轮消除的外部限制，PM可接受“按所列上游限制完成”，同时保留逐项限制。仍可继续执行的排队/分页、尚未尝试、未修复错误或仅因运行时间到达而停止的任务，结论必须是“部分完成，待继续”，并保留恢复路径。

这份任务的验收针对执行覆盖与数据留存，不对全部市场召回率、文本识别准确率、贷款牌照或法律合规作保证。CEO/CTO执行真实任务，Alex独立核对结果，PM最后给出正式结论；PM不直接修改真实数据库或任务。
